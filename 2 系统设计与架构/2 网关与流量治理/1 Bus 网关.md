# 1 Bus 网关

## 1.1 基础概念

- **消息总线（Message Bus）**：服务通过共享的消息基础设施交换命令和事件，而不是彼此直接调用。Kafka、RabbitMQ、RocketMQ 等都可承担消息总线的角色。它的价值在于异步解耦、削峰和独立扩展。
- **API 网关（Gateway）**：系统对外的统一入口，通常负责路由、认证鉴权、限流、协议转换和观测。常见实现包括 Nginx、Spring Cloud Gateway、Kong 和 Envoy。

**Bus 网关（Bus Gateway）不是一个统一标准或某个特定产品，而是一种架构模式**：网关在 HTTP、gRPC、WebSocket 等边界协议与内部消息总线之间适配，使外部调用者无需直接访问内部 Topic、Broker 或服务。

## 1.2 解决的问题与边界

Bus 网关适合将外部请求转换为内部异步命令，或将内部事件安全地分发给外部消费者。例如，客户端提交导出任务后立即得到任务 ID；导出完成事件经网关推送到 WebSocket，或由网关触发已登记的 Webhook。

它不应成为所有服务调用的必经中转层。读取详情、短事务写入等需要低延迟同步响应的场景，通常仍适合由 API 网关路由到后端服务；内部服务之间的强一致同步协作也不应被“先发消息再等待”机械替代。

```text
客户端 ── HTTP/gRPC ──> Bus 网关 ──> 命令 Topic ──> 订单服务
   ^                         │                              │
   │                         │                              v
   └─ WebSocket / Webhook ───┴──── 领域事件 Topic <──────────┘
```

## 1.3 两类交互模型

### 1.3.1 异步命令与事件推送

外部请求被转换为命令并写入总线；网关返回 `202 Accepted` 和 `operation_id`，消费者稍后执行。业务服务发布状态事件，网关再把事件投递为 WebSocket、Server-Sent Events（SSE）或 Webhook。

这是默认推荐的模型。它将请求峰值缓冲在消息系统中，也避免网关长时间占用 HTTP 连接。客户端应通过查询接口或订阅结果事件获取最终状态。

### 1.3.2 请求—应答

对于确实需要同步结果的短操作，网关可写入请求 Topic，同时订阅响应 Topic，并以 `correlation_id` 匹配响应。必须设置严格超时、并发上限和取消策略；超时只表示调用方未等到结果，不等价于命令没有被消费。因此下游操作仍必须幂等。

```text
HTTP 请求 -> 网关 -> request Topic -> 消费者
    ^                                 |
    |---- correlation_id <--- reply Topic <---|
```

不要把请求—应答模式用于长任务、批量任务或高扇出操作。此类场景应改用异步任务模型。

## 1.4 核心能力

| 能力 | 说明 |
| :--- | :--- |
| 协议适配 | 将 REST、gRPC 等请求映射为命令/事件，并将内部事件映射为 Webhook、SSE 或 WebSocket。 |
| 路由与隔离 | 按租户、业务域、Topic 和消费者组路由；禁止客户端任意指定内部 Topic。 |
| 身份与授权 | 在边界校验 OAuth 2.0/OIDC、mTLS 或签名；将可信调用方、租户和权限写入消息上下文。 |
| 流量治理 | 请求限流、消息大小限制、并发和积压阈值、超时与熔断，防止入口流量耗尽 Broker 或下游资源。 |
| 可靠投递 | 明确确认时机、重试、死信队列（DLQ）和告警策略，避免失败消息被悄然丢弃。 |
| 观测与审计 | 透传 trace ID，记录请求、消息 ID、Topic、消费者、投递结果和脱敏后的审计信息。 |

## 1.5 消息契约与演进

不要把 HTTP 请求原样序列化后直接发送。应定义稳定的消息契约，并把业务载荷与传输元数据分开。以下字段可放在 Header 或信封中：

```json
{
  "message_id": "01J...",
  "correlation_id": "req-7f3c",
  "causation_id": "01J...",
  "event_type": "order.created",
  "schema_version": 1,
  "occurred_at": "2026-08-24T10:00:00Z",
  "tenant_id": "tenant-a",
  "traceparent": "00-...",
  "data": {
    "order_id": "o-1001"
  }
}
```

- `message_id` 用于去重和排查；`correlation_id` 串联一次外部请求及其响应；`causation_id` 表示触发当前消息的上游消息。
- 事件类型应表达已发生的事实，例如 `order.created`；命令应表达意图，例如 `CreateOrder`，两者不应混用。
- 使用 JSON Schema、Protobuf 或 Avro 等机制管理契约。演进时优先新增可选字段，消费者应忽略未知字段；删除或改变字段语义前，需要经历兼容期和消费者迁移。
- 业务错误应有稳定的错误码与可公开的错误信息，内部堆栈、Topic 名称和基础设施细节不应暴露给客户端。

## 1.6 可靠性、一致性与顺序

大多数消息系统提供的是**至少一次投递**：网络故障或确认超时会导致重复消息。因此消费者必须按 `message_id` 或业务唯一键实现幂等，例如使用唯一约束、幂等记录表或状态机检查。不能假设“消息只会到达一次”。

发布业务数据和事件时，避免在“数据库提交成功但消息发送失败”与反向情况之间留下不一致。常用的 **Transactional Outbox** 模式是在同一数据库事务中写业务数据和 outbox 记录，再由独立发布器可靠地投递到总线。消费者侧可结合 Inbox/去重记录实现端到端的至少一次处理。

顺序通常只在同一分区键内成立。将同一订单、账户等聚合根 ID 作为消息键，才能尽量保证该实体的处理顺序；不要承诺跨 Topic、跨分区或全局顺序。重试时应区分可重试的暂态错误和不可重试的业务错误，超过阈值的消息进入 DLQ，并提供人工修复、重放与审计流程。

## 1.7 安全设计

- Broker 只暴露给受控网络和服务身份，客户端不得借由网关获得任意生产/消费 Topic 的权限。
- 网关对每个路由维护“调用方—业务能力—Topic”的白名单，并按租户隔离消息和消费权限。
- 校验消息大小、字段格式、签名和时间戳；敏感字段按需加密或脱敏，日志与 DLQ 同样要遵守数据分级要求。
- Webhook 必须使用 HTTPS、签名验证、超时和重试退避；避免跟随不可信重定向，以防 SSRF。

## 1.8 可观测性与容量治理

至少监控入口请求量与错误率、Topic 写入失败率、生产/消费延迟、消费积压（lag）、重试次数、DLQ 数量、Webhook 投递成功率以及请求—应答超时率。告警应关联 `trace_id`、`message_id` 和 `correlation_id`，以便从一次外部请求追踪到具体消费者。

对慢消费者和下游故障实施背压：限制单租户并发与配额、暂停或降速事件分发、控制重试速率。重放消息前要确认消费者幂等性、保留期、影响范围和审计要求，避免一次重放再次触发外部副作用。

## 1.9 设计检查清单

- 此接口是否真的需要异步化？若需要，是否返回了可查询的 `operation_id`？
- 命令、事件、响应的 Topic、分区键、保留期和权限边界是否已定义？
- 是否定义了超时、重试、DLQ、幂等与重放流程？
- 消息契约是否有版本策略、兼容性测试和废弃计划？
- 是否透传链路追踪并对敏感数据进行了脱敏？
- 删除、退款、扣款等有外部副作用的操作，是否具备幂等键和人工补偿方案？
