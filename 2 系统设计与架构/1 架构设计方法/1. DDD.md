# DDD
## 1. 什么是 DDD

DDD（Domain-Driven Design，领域驱动设计）是一种以业务领域为中心的软件设计方法。它的核心不是“套一组固定分层”，而是通过统一语言、领域模型和边界划分，把复杂业务拆解成可演进、可协作、可落地的系统结构。

DDD 主要解决三类问题：

- 复杂业务概念混乱，研发和业务沟通成本高。
- 系统边界模糊，导致模块高耦合、职责不清。
- 代码只围绕表和接口编写，无法表达业务规则与业务约束。

一句话理解：DDD 的重点是先设计业务模型，再让代码结构服从业务模型。

## 2. DDD 的核心思想

DDD 的核心可以概括为四点：

- 以领域为中心：系统设计围绕业务能力展开，而不是围绕数据库表或技术框架展开。
- 统一语言：产品、业务、研发使用同一套术语描述核心概念，减少歧义。
- 划分边界：通过限界上下文明确模型适用范围，降低跨模块耦合。
- 模型驱动实现：领域模型不是文档，而是直接映射到代码中的对象、行为和规则。

## 3. DDD 全景

DDD 通常分为两层：

- 战略设计：解决“系统怎么划边界”。
- 战术设计：解决“边界内部怎么建模和编码”。

常见理解路径如下：

1. 先识别业务领域、子域和核心能力。
2. 再划分限界上下文，明确每个上下文内的模型边界。
3. 再定义上下文之间的集成关系。
4. 最后在单个上下文内部使用实体、值对象、聚合、领域服务等完成编码。

## 4. 战略设计

### 4.1 领域、子域、核心域

领域是业务问题空间，例如电商、支付、物流。

子域是领域下进一步拆分的业务板块，通常分为：

- 核心域：决定系统竞争力的关键能力，最值得投入设计和研发资源。
- 支撑域：服务核心域但不直接构成竞争优势的能力。
- 通用域：行业内相对通用的能力，可以复用成熟方案或外部系统。

示例：

- 电商领域中的商品推荐、定价策略可能属于核心域。
- 库存、会员可能属于支撑域。
- 短信、认证、文件存储通常更接近通用域。

### 4.2 限界上下文

限界上下文（Bounded Context）是 DDD 中最关键的边界概念，表示某个领域模型成立的范围。

同一个词在不同上下文中含义可能不同，例如“订单”：

- 在交易上下文中，订单关注下单、支付、履约状态。
- 在财务上下文中，订单关注应收、结算、退款对账。

因此，DDD 并不追求一个全局统一大模型，而是追求“上下文内统一，上下文间明确映射”。

### 4.3 上下文映射

多个限界上下文之间需要定义协作关系，常见模式包括：

- Open Host Service：提供公开协议供其他上下文调用。
- Anti-Corruption Layer：通过防腐层隔离外部模型污染。
- Conformist：下游直接遵从上游模型。
- Shared Kernel：共享一小部分稳定模型，但必须严格控制范围。

实践上，上下文映射解决的是：

- 接口怎么定义。
- 模型怎么翻译。
- 谁依赖谁。
- 谁对变更负责。

## 5. 战术设计

战术设计主要作用于单个限界上下文内部，用于表达业务规则和约束。

### 5.1 实体（Entity）

实体有唯一标识，关注“身份连续性”，即使属性变化，仍然是同一个对象。

例如：

- 用户
- 订单
- 商品

判断是否为实体的关键不是“要不要建表”，而是“它是否有持续身份”。

### 5.2 值对象（Value Object）

值对象没有唯一标识，关注的是属性值本身，通常应设计为不可变。

例如：

- 金额
- 地址
- 时间区间

值对象适合封装一组天然绑定的属性和校验逻辑，避免这些逻辑散落在多个类中。

### 5.3 聚合与聚合根（Aggregate / Aggregate Root）

聚合是一组具有强一致性边界的对象集合，聚合根是对外暴露的唯一访问入口。

原则：

- 外部对象只能引用聚合根，不能直接修改聚合内部成员。
- 一个事务通常只应修改一个聚合。
- 聚合边界用于保护业务不变量。

示例：

- 订单聚合中，订单项、收货信息、优惠明细都受订单聚合根约束。
- “订单总金额必须等于订单项金额之和”就是聚合内不变量。

### 5.4 领域服务（Domain Service）

当某个业务行为不自然归属于单个实体或值对象时，可以放到领域服务中。

适用场景：

- 涉及多个聚合的业务规则协调。
- 需要表达重要领域动作，但又不属于基础设施能力。

不要把所有业务逻辑都塞进领域服务，否则容易退化成贫血模型。

### 5.5 仓储（Repository）

仓储用于提供面向领域对象的持久化抽象，屏蔽底层数据库实现细节。

仓储的目标不是“写 CRUD 工具类”，而是让领域层以聚合为单位进行加载和保存。

常见原则：

- 一个仓储通常对应一个聚合根。
- 仓储接口定义在领域层，实现在基础设施层。
- 不要让业务层直接拼 SQL 操作多个聚合破坏边界。

### 5.6 工厂（Factory）

当对象创建逻辑复杂、需要满足多个约束或组合多个值对象时，可以使用工厂封装创建过程。

它的价值在于：

- 保证创建即合法。
- 隐藏复杂组装过程。
- 避免上层随意 new 导致对象处于无效状态。

### 5.7 领域事件（Domain Event）

领域事件表示“领域内已经发生的重要事实”，例如：

- 订单已创建
- 支付已完成
- 库存已锁定

用途：

- 解耦聚合之间的协作。
- 驱动跨上下文异步处理。
- 记录关键业务行为。

领域事件强调业务语义，不等同于技术消息。消息队列只是它的一种传递手段。

## 6. 代码分层

DDD 常见实现方式会结合分层架构或六边形架构，典型职责如下：

### 6.1 用户接口层

负责接收外部请求，例如：

- Controller
- API
- RPC 接口
- 消费消息入口

该层只负责协议转换、参数校验和调用应用服务，不承载核心业务规则。

### 6.2 应用层

应用层负责用例编排，不负责核心业务规则。

主要职责：

- 组织一个完整业务流程。
- 控制事务。
- 调用领域对象完成业务动作。
- 发布集成事件。
- 返回 DTO 或视图模型。

应用层回答的是“做什么流程”，领域层回答的是“业务规则是什么”。

### 6.3 领域层

领域层是 DDD 的核心，承载：

- 实体
- 值对象
- 聚合
- 领域服务
- 仓储接口
- 领域事件

领域层应该尽量保持纯净，不依赖 Web、ORM、MQ 等技术细节。

### 6.4 基础设施层

基础设施层负责技术实现，例如：

- 数据库访问
- 缓存
- 消息队列
- 第三方服务接入
- 仓储实现

它服务于领域层和应用层，而不反过来主导模型设计。

## 7. DDD 与微服务的关系

DDD 不等于微服务，但非常适合指导微服务拆分。

关系可以这样理解：

- DDD 关注业务建模和边界划分。
- 微服务关注部署边界、运行边界和团队边界。

理想情况下：

- 一个限界上下文可以演进为一个微服务。
- 但一个微服务也可能承载多个较小上下文。
- 如果领域边界不清晰，微服务拆分通常会失败。

所以，DDD 是微服务拆分的重要前置方法，但不是唯一方法。

## 8. DDD 与事件驱动的关系

DDD 与事件驱动架构经常一起使用，原因在于：

- 聚合内部保证强一致性。
- 聚合之间通过领域事件或集成事件进行最终一致性协作。
- 跨上下文通信天然适合异步解耦。

常见组合方式：

- 聚合内同步修改状态。
- 提交事务后发布领域事件。
- 再由应用层或集成层转换为消息事件推送到 MQ。

这类设计常见于订单、库存、支付、履约等流程协同场景。

## 9. DDD 的落地步骤

一个更实用的落地顺序如下：

1. 先梳理核心业务流程，识别关键术语和业务规则。
2. 与业务方统一语言，形成术语表。
3. 划分子域，识别核心域、支撑域、通用域。
4. 划分限界上下文，明确每个上下文的职责和边界。
5. 定义上下文之间的集成方式与模型映射。
6. 在上下文内部识别聚合、实体、值对象和领域事件。
7. 再落到代码分层、仓储设计、事务边界和消息协作。

如果直接从表结构和接口开始设计，通常会绕开 DDD 的核心价值。

## 10. DDD 常见误区

### 10.1 把 DDD 等同于“多建几个类”

DDD 不是把 Java 类拆细，也不是给 CRUD 项目增加几个名词。没有领域边界和业务模型，只有类名变化，不能算 DDD。

### 10.2 把所有逻辑都放到 Service

如果实体只有 getter/setter，所有逻辑都堆在 Service 中，本质上还是贫血模型，领域对象没有承载业务规则。

### 10.3 聚合设计过大

很多系统把多个对象强行塞进一个大聚合，导致：

- 事务过大
- 锁冲突严重
- 性能差
- 并发能力弱

聚合应该围绕不变量设计，而不是围绕“查询方便”设计。

### 10.4 试图建立一个全局统一模型

DDD 强调限界上下文，不同上下文允许存在不同模型。强行统一所有概念，往往会得到一个谁都不满意的大泥球模型。

### 10.5 机械套用 DDD

简单 CRUD 后台、低复杂度工具系统不一定需要完整 DDD。DDD 更适合规则复杂、概念密集、演进频繁的核心业务系统。

## 11. 什么时候适合用 DDD

适合场景：

- 业务概念复杂，规则多且变化快。
- 多团队协作，术语和边界容易混乱。
- 系统需要长期演进，不能只靠短期堆功能。
- 核心链路需要清晰表达业务约束和领域知识。

不太适合的场景：

- 非核心后台管理系统。
- 逻辑简单、以录入查询为主的系统。
- 团队当前连基本模块边界和编码规范都还未建立。

## 12. 一句话总结

DDD 不是一种固定代码模板，而是一套围绕业务复杂度进行建模、划边界、统一语言并指导实现的设计方法。

可以把它理解为：

- 战略设计解决边界问题。
- 战术设计解决建模问题。
- 分层架构解决落地问题。
- 事件和上下文映射解决协作问题。

当业务真正复杂时，DDD 的价值不在“概念多”，而在“让复杂性被正确地安放在合适的边界内”。
