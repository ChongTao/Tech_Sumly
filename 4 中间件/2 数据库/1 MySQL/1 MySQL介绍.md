# 1 MySQL 介绍

MySQL 是广泛使用的开源关系型数据库管理系统。它使用表、行、列和 SQL 组织数据，适合订单、账户、商品、后台管理等需要事务和关联查询的业务场景。生产环境通常使用 InnoDB 存储引擎。

## 1.1 核心特点

- 关系模型清晰，支持主键、外键、唯一约束和多表关联。
- InnoDB 支持 ACID 事务、行级锁、崩溃恢复和外键。
- 使用 B+ 树索引加速等值、范围和排序查询。
- 支持主从复制、读写分离和分库分表等扩展方案。
- SQL 生态成熟，适合结构稳定且一致性要求较高的数据。

## 1.2 基本概念

| 概念 | 说明 |
| :--- | :--- |
| database | 数据库，包含一组相关表 |
| table | 表，按固定结构保存数据 |
| row | 行，一条记录 |
| column | 列，记录的一个属性 |
| primary key | 主键，唯一标识一行数据 |
| index | 索引，用空间换查询效率 |
| storage engine | 存储引擎，决定数据存储、锁和事务能力 |

## 1.3 InnoDB 与事务

InnoDB 是 MySQL 的默认存储引擎。它通过 redo log 保证已提交数据可恢复，通过 undo log 支持回滚与多版本并发控制（MVCC），并使用 binlog 记录逻辑变更以支持复制和恢复。

事务应满足 ACID：

- 原子性：事务中的操作要么全部成功，要么全部回滚。
- 一致性：事务前后均满足业务约束。
- 隔离性：并发事务之间按隔离级别互不干扰。
- 持久性：已提交的数据在故障后仍可恢复。

常用隔离级别为 `READ COMMITTED` 和 `REPEATABLE READ`。MySQL InnoDB 默认使用 `REPEATABLE READ`；涉及范围更新或锁定读取时，还应关注间隙锁、临键锁及死锁风险。

## 1.4 索引要点

- 主键索引的叶子节点保存整行数据；二级索引的叶子节点保存主键值。
- 联合索引遵循最左前缀原则，例如 `(user_id, status, created_at)` 可用于以 `user_id` 开头的条件组合。
- 避免在索引列上做函数计算、隐式类型转换或前导通配符模糊查询，这些情况可能无法有效使用索引。
- 索引不是越多越好；索引会占用空间，并增加写入、更新和维护成本。
- 使用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 验证执行计划，而不是只凭经验添加索引。

### 1.4.1 索引类型与适用场景

InnoDB 的普通索引和唯一索引通常都是 B+ 树；它按索引键有序保存，适合等值查询、范围查询、排序和前缀匹配。主键索引属于聚簇索引：叶子节点保存完整行；二级索引的叶子节点保存二级索引列和主键值，查询的列不在二级索引中时，通常还需要根据主键回表。

| 类型 | 作用 | 典型场景 | 注意事项 |
| :--- | :--- | :--- | :--- |
| PRIMARY KEY | 唯一标识一行，并决定 InnoDB 的聚簇顺序 | `id`、业务稳定的唯一编号 | 每张 InnoDB 表只有一个；主键应尽量短、稳定且递增趋势明显 |
| UNIQUE | 保证列或列组合不重复 | 邮箱、订单号、租户内的编码 | `NULL` 值可出现多次；同时承担查询索引的角色 |
| 普通索引（KEY/INDEX） | 提升查询、连接、排序效率 | `user_id`、`created_at`、状态与时间组合 | 不保证唯一性，写入时需要维护 |
| 联合索引 | 为多个连续条件提供一个有序访问路径 | `(tenant_id, status, created_at)` | 遵循最左前缀；列顺序需由实际查询决定 |
| 全文索引（FULLTEXT） | 对长文本分词检索 | 文章标题、正文搜索 | 适合关键词检索，不替代 B+ 树的精确过滤 |
| 空间索引（SPATIAL） | 加速空间对象查询 | 地理位置、范围关系 | 仅用于空间数据类型及对应函数 |

设计联合索引时，先收集高频 SQL，再综合考虑等值过滤列、范围列、排序列和返回列。通常将等值过滤列放前面；范围条件之后的列往往不能继续用于索引定位，但在部分场景仍可减少回表或避免额外排序。若查询所需列都包含在二级索引中，优化器可使用覆盖索引，减少回表。

索引失效不等于完全不使用索引。优化器会基于统计信息和成本选择路径；当选择性很低、返回行过多，或全表扫描更便宜时，它可能主动不走索引。变更索引前后都应以 `EXPLAIN ANALYZE` 的实际行数与耗时为准，并定期通过 `ANALYZE TABLE` 更新明显陈旧的统计信息。

### 1.4.2 索引设计清单

- 为主键、唯一业务约束、外键列和常用关联列建立合适索引；外键所需的子表索引由 InnoDB 自动创建时，也应检查其是否能满足业务查询。
- 避免冗余索引：已有 `(a, b)` 时，单列 `(a)` 通常重复；但 `(b)` 仍可能有价值。是否删除应依据真实 SQL 验证。
- 让比较两侧类型、长度和字符集尽量一致；例如不要用字符串参数查询整数索引列，以免发生隐式转换。
- 大字段、低选择性字段（如只有少数取值的性别、开关）不宜单独建索引；可与选择性较好的过滤列组成联合索引。
- 写多读少的表要克制建索引。每个二级索引都会增加 `INSERT`、`UPDATE`、`DELETE` 的维护、页分裂和存储成本。

## 1.5 外键与引用完整性

外键（foreign key）是子表中一列或多列到父表候选键的引用约束。它把“订单必须属于存在的用户”这类关系交给数据库校验，防止插入孤儿记录，也限制或级联处理父记录的更新和删除。MySQL 中外键由 InnoDB 支持；父表和子表应使用 InnoDB，关联列的类型、长度、无符号属性以及字符串列的字符集和排序规则必须兼容。

外键引用的父表列必须有索引，通常是主键或唯一键；子表外键列也必须有索引。若子表缺少合适的索引，InnoDB 可能自动创建一个。外键约束名在同一 schema 内必须唯一。由于校验和级联会带来额外锁、写入与运维复杂度，跨服务、跨库分片或高并发核心链路常改用应用层校验、异步对账等方式；但这意味着应用必须承担一致性保障，不能只因性能考虑而忽略数据治理。

| 动作 | 父表删除或更新被引用值时的行为 | 适用场景 |
| :--- | :--- | :--- |
| `RESTRICT` / `NO ACTION` | 拒绝操作（MySQL InnoDB 中两者效果相同） | 不允许存在子记录时删除父记录 |
| `CASCADE` | 同步删除子记录，或同步更新子表外键值 | 明确的从属关系，如订单项随订单删除 |
| `SET NULL` | 将子表外键列设为 `NULL` | 关系可解除，且子表列允许为 `NULL` |
| `SET DEFAULT` | MySQL 解析该语法但 InnoDB 不支持 | 不应作为 MySQL 方案依赖 |

外键不是索引的替代品：它解决引用完整性，索引解决访问效率。生产设计时应明确删除语义，谨慎使用大范围 `CASCADE`；级联操作会在同一事务中执行，可能扩大锁定范围。导入历史数据、批量迁移或删除父记录前，要先评估现有引用关系；不要长期依赖 `SET FOREIGN_KEY_CHECKS = 0` 绕过校验，否则可能留下无法恢复的脏引用。

## 1.6 使用建议

- 为表定义明确的主键；大多数业务表适合使用递增或趋势递增的主键。
- 金额使用 `DECIMAL`，时间统一约定时区，布尔/枚举状态使用语义明确的字段值。
- 事务保持短小，按固定顺序访问资源，降低锁等待和死锁概率。
- 分页优先使用基于主键或排序字段的游标分页；深度 `LIMIT offset` 分页会越来越慢。
- 定期备份并演练恢复；高可用不能替代备份。
