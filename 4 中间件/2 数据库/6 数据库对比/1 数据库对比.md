# 1 数据库对比

本章从类型定位、数据模型、事务能力、查询方式、扩展手段和许可协议等角度，对比 MySQL、PostgreSQL、Redis、MongoDB。四者属于不同类型，定位并不相同，实际系统中往往组合使用而非互相替代。

## 1.1 总体对比

| 维度 | MySQL | PostgreSQL | Redis | MongoDB |
| :--- | :--- | :--- | :--- | :--- |
| 类型 | 关系型数据库 | 对象关系型数据库 | 内存键值数据库 | 文档数据库 |
| 数据模型 | 表、行、列 | 表、行、列，另有 JSONB、数组等 | 字符串、哈希、列表、集合、有序集合、流等 | BSON 文档，支持嵌套对象与数组 |
| schema 约束 | 严格，需预先定义表结构 | 严格，但可用 JSONB 承载半结构化数据 | 无 schema，按键组织数据 | 宽松，不同文档字段可以不同 |
| 查询接口 | SQL | 功能丰富的 SQL，标准兼容性强 | 命令按键访问，复杂查询能力有限 | MQL 与聚合管道 |
| 事务 | InnoDB 支持 ACID 事务 | 完整支持 ACID | 单命令原子，MULTI 与 Lua 提供基本原子性 | 4.0 起支持多文档 ACID 事务 |
| 存储介质 | 磁盘为主 | 磁盘为主 | 内存为主，磁盘做持久化 | 磁盘为主 |
| 水平扩展 | 主从复制，分库分表依赖中间件 | 主从与逻辑复制，可用 Citus 分片 | 副本集、Cluster 分片 | 原生分片（分片集群） |
| 许可协议 | GPLv2（另有商业许可） | PostgreSQL License（宽松） | Redis 8 为 AGPLv3/RSALv2/SSPLv1 三重许可 | SSPL |

## 1.2 索引对比

### 1.2.1 有无索引的区别

索引是用于加速定位数据行的有序辅助结构。有无索引的区别主要体现在：

| 维度 | 无索引 | 有索引 |
| :--- | :--- | :--- |
| 查找方式 | 全表（全集合）扫描，逐行比对 | 先在索引中定位目标范围，再读取对应数据 |
| IO 量 | 与全表数据量成正比 | 与命中行数相关，通常远小于全表 |
| 排序 | `ORDER BY` 需要额外排序操作 | 可直接利用索引的有序性，避免排序 |
| 写入代价 | 较低 | 插入、更新、删除都需同步维护索引结构 |
| 空间开销 | 无 | 索引占用额外存储空间 |

使用时需要注意：

- 小表或需要全表聚合的查询，全表扫描可能比走索引更快，优化器也可能主动放弃索引。
- 选择性过低的索引（如只有少数取值的列）通常无法有效减少扫描行数。
- 每个二级索引都会增加写入与维护成本，索引应按真实查询建立，并用执行计划验证效果。

### 1.2.2 各数据库索引能力

| 数据库 | 常见索引类型 | 说明 |
| :--- | :--- | :--- |
| MySQL（InnoDB） | B+ 树、全文、空间索引 | 聚簇索引叶子节点存整行；二级索引叶子节点存主键值，回表读取完整行 |
| PostgreSQL | B-tree、Hash、GIN、GiST、BRIN | GIN 适合多值与全文，GiST 适合几何数据，BRIN 适合数据有序的大表 |
| Redis | 无传统二级索引 | 按键访问数据；sorted set 支持有序范围查询，RediSearch 等模块可补充索引能力 |
| MongoDB | B-tree、多键、文本、地理空间、哈希 | 支持对嵌套文档字段建索引；哈希索引可用作分片键 |

## 1.3 存储过程

存储过程是预先编译并保存在数据库服务器端的一组 SQL 与控制流逻辑，按名称调用，可接收输入输出参数。它适合封装批处理和统一的业务规则，但各数据库语法差异大，是常见的厂商绑定来源。

### 1.3.1 基本概念

| 概念 | 说明 |
| :--- | :--- |
| procedure | 用 `CALL` 调用，可包含事务控制，不强制返回值 |
| function | 在表达式中调用，必须返回值，对副作用的限制因数据库而异 |
| trigger | 由插入、更新、删除事件自动触发，不能手动调用 |
| 参数模式 | IN 输入、OUT 输出、INOUT 双向，各数据库支持程度不同 |

过程体除 SQL 外，通常还支持变量声明、条件分支（IF/CASE）、循环（WHILE/LOOP/FOR）、游标（逐行处理）和异常处理。

### 1.3.2 优缺点

优点：

- 一次调用完成多条 SQL，减少网络往返。
- 业务规则集中在数据库端，多个应用入口的逻辑保持一致。
- 执行计划可缓存复用，减少重复解析开销（程度因数据库而异）。
- 可只授予过程的执行权限而不开放表权限，收窄权限面。

缺点：

- 调试、单测和版本管理不如应用代码方便，变更与回滚成本高。
- 语法和能力在不同数据库间差异明显，迁移成本高。
- 逻辑在数据库服务器上执行，加重数据库负载，不利于水平扩展。
- 业务逻辑分散在数据库与应用两层，排查与协作成本上升。

### 1.3.3 语法示例

```sql
-- MySQL
DELIMITER $$
CREATE PROCEDURE deactivate_user(IN target_id INT)
BEGIN
  UPDATE users SET status = 0 WHERE id = target_id;
END$$
DELIMITER ;

CALL deactivate_user(1);
```

```sql
-- PostgreSQL
CREATE PROCEDURE deactivate_user(target_id INT)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE users SET status = 0 WHERE id = target_id;
END;
$$;

CALL deactivate_user(1);
```

### 1.3.4 各数据库支持情况

| 数据库 | 支持情况 | 说明 |
| :--- | :--- | :--- |
| MySQL | `CREATE PROCEDURE` / `CREATE FUNCTION` | 过程体支持控制流与游标，用 `CALL` 调用；调试工具有限 |
| PostgreSQL | `CREATE PROCEDURE`（11+）/ `CREATE FUNCTION` | 可用 PL/pgSQL 等多种语言编写；过程体内可控制事务；函数可直接在 SQL 中使用 |
| Redis | 无存储过程 | Lua 脚本（`EVAL`/`EVALSHA`）提供原子化的服务端逻辑；6.2 起可用 Functions 管理脚本 |
| MongoDB | 无存储过程 | 聚合管道封装查询逻辑；聚合中的 `$function` 可执行自定义 JS |

使用建议：

- 高频迭代的业务逻辑放在应用层；稳定、少变的批处理、数据清洗和运维脚本适合用存储过程。
- 引入前评估团队能力与未来迁移成本；确需使用时保持过程逻辑轻薄，避免把复杂业务埋进数据库。

## 1.4 能力定位差异

### 1.4.1 MySQL 与 PostgreSQL

两者都是成熟的关系型数据库，都支持 SQL、事务和主从复制，差异主要在侧重点：

| 维度 | MySQL | PostgreSQL |
| :--- | :--- | :--- |
| 生态 | 生态广泛，读写分离与分库分表方案成熟 | 生态活跃，扩展机制丰富 |
| 数据类型 | 常规类型与 JSON 支持 | 类型丰富，含 JSONB、数组、hstore |
| 扩展能力 | 可插拔存储引擎 | PostGIS、TimescaleDB 等扩展 |
| 标准兼容 | 有自身约定 | SQL 标准兼容性强 |
| 典型定位 | OLTP 业务系统、互联网应用 | 复杂查询、GIS、数据分析等混合负载 |

### 1.4.2 Redis 与关系型数据库

- Redis 数据驻留内存，读写延迟在微秒级，但容量受内存成本限制。
- 适合缓存、会话、计数器、排行榜、分布式锁、消息队列（stream）等场景。
- RDB 与 AOF 持久化不能完全替代关系型数据库的事务与一致性保障，通常不作为核心业务数据的主存储。

### 1.4.3 MongoDB 与关系型数据库

- 文档可嵌套对象和数组，天然贴合档案、内容、事件等层级数据。
- schema 宽松，适合字段频繁变化的场景，但数据一致性需要应用层配合保障。
- 事务与多表关联能力弱于关系型数据库；数据模型应按查询模式设计，避免过度依赖 `$lookup` 做连接。

## 1.5 典型场景参考

| 场景 | 常见选择 | 说明 |
| :--- | :--- | :--- |
| 订单、支付、账户 | MySQL / PostgreSQL | 需要强事务与引用完整性 |
| 复杂查询、GIS、统计分析 | PostgreSQL | 类型与扩展生态占优 |
| 缓存、排行榜、会话、分布式锁 | Redis | 低延迟、数据结构丰富 |
| 内容管理、日志、IoT 数据 | MongoDB | schema 灵活、写入吞吐好 |
| 全文检索与复杂过滤 | 专用搜索引擎 | 不属于本章四类数据库的强项 |

## 1.6 选型建议

- 业务有明确表结构和事务要求时，优先选择关系型数据库：团队熟悉、运维方案成熟选 MySQL；复杂查询、丰富类型需求多选 PostgreSQL。
- 读多写少、热点明显的场景叠加 Redis 缓存，同时提前设计缓存与数据库的一致性策略。
- 数据结构不稳定或嵌套层级深时使用 MongoDB；资金、订单等核心数据仍建议放在关系型数据库。
- 真实系统常见组合是关系型数据库做主存储、Redis 做缓存、搜索引擎做检索；选型还需评估团队熟悉度、运维能力与备份恢复方案。
- 最终决策前应使用真实数据量和查询模式做压测，而不是只对比功能列表。
