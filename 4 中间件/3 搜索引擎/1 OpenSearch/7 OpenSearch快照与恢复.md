# 一 OpenSearch 快照与恢复

副本解决的是高可用，不是备份。误删索引、误操作覆盖数据、集群整体故障，都需要依赖快照恢复。

## 1.1 为什么需要快照

以下场景副本通常无能为力：

- 手工删除了索引
- 应用错误批量更新了数据
- 集群磁盘损坏或节点整体丢失
- 迁移或升级失败，需要回滚

因此生产环境应把快照当成标准配置，而不是事故后再补。

## 1.2 快照包含什么

快照通常用于备份：

- 索引数据
- 部分元数据
- 集群中的相关配置状态

恢复时可以按粒度选择：

- 恢复整个快照
- 恢复指定索引
- 恢复到新索引名，避免直接覆盖

## 1.3 基本流程

### 1. 注册快照仓库

不同环境可选择不同仓库类型，例如共享文件系统或对象存储。

```json
PUT /_snapshot/my_backup
{
  "type": "fs",
  "settings": {
    "location": "/mnt/opensearch-backup"
  }
}
```

### 2. 创建快照

```json
PUT /_snapshot/my_backup/snapshot_20260610
{
  "indices": "users,orders",
  "ignore_unavailable": true,
  "include_global_state": false
}
```

### 3. 查看快照

```bash
GET /_snapshot/my_backup/_all
```

### 4. 恢复快照

```json
POST /_snapshot/my_backup/snapshot_20260610/_restore
{
  "indices": "users",
  "include_global_state": false
}
```

## 1.4 恢复时的常见做法

### 恢复到新索引

生产环境里，更稳妥的方式通常不是直接覆盖，而是先恢复到新索引，再比对数据后切别名。

```json
POST /_snapshot/my_backup/snapshot_20260610/_restore
{
  "indices": "users",
  "rename_pattern": "users",
  "rename_replacement": "users_restore"
}
```

这样可以：

- 避免误覆盖线上索引
- 便于对比恢复前后的数据
- 结合别名做回切

## 1.5 快照策略设计

要回答这几个问题：

- 多久做一次快照
- 快照保留多久
- 全量还是按时间滚动
- 恢复目标时间点要求是什么

常见思路：

- 核心业务索引：频率更高、保留更久
- 日志类索引：按生命周期和成本平衡
- 重要变更前：额外做一次临时快照

## 1.6 快照不等于“可恢复”

很多团队只做了“创建快照”，但没有验证“恢复是否真的可用”。这不够。

至少要定期验证：

- 仓库权限是否正常
- 快照是否能成功完成
- 恢复速度是否满足要求
- 恢复后的索引是否能正常查询

如果从未演练过恢复，事故时快照可能只是心理安慰。

## 1.7 常见注意事项

- 恢复前确认目标索引是否已存在，避免命名冲突。
- 不要默认恢复全局状态，除非明确需要。
- 大体量恢复会占用网络、磁盘和集群资源，应评估窗口期。
- 备份仓库本身也要有访问控制，不能谁都能读写。

## 1.8 实践建议

- 备份策略和恢复演练要配套存在。
- 高风险操作前先做临时快照，例如重建索引、升级、批量修复数据。
- 恢复优先走“恢复到新索引 + 校验 + 别名切换”流程。
- 备份目标应与主集群故障域隔离，否则一起损坏时没有意义。
