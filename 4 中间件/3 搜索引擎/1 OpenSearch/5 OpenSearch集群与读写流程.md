# 一 OpenSearch 集群与读写流程

OpenSearch 是分布式搜索引擎。理解节点、分片、副本，以及一次写入和一次查询在集群里的流转过程，比单纯记 API 更重要。

## 1.1 集群基本组成

- 集群：一组协同工作的 OpenSearch 节点。
- 节点：一个运行中的 OpenSearch 实例。
- 索引：文档集合。
- 主分片：真正承载数据的分片。
- 副本分片：主分片的复制品，用于高可用和读扩展。

一个索引创建时，通常至少要决定：

- `number_of_shards`
- `number_of_replicas`

```json
PUT /orders
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}
```

这表示：

- 数据会分布到 3 个主分片
- 每个主分片有 1 个副本
- 总分片数 = 3 主分片 + 3 副本分片

## 1.2 分片与副本的作用

### 分片

分片的核心作用是把一个大索引拆开，便于横向扩展：

- 单机放不下的数据可以分散到多台机器
- 查询可以并行执行
- 写入压力可以分散

### 副本

副本的核心作用：

- 提高可用性，主分片所在节点故障时可顶上
- 提高读取吞吐，搜索可以从主分片或副本分片读取

注意：

- 副本不会提升单条写入性能
- 节点数不足时，副本可能无法分配，集群状态会变成 `yellow`

## 1.3 写入流程

一次文档写入，大致流程如下：

1. 客户端把请求发给任意一个节点。
2. 该节点作为协调节点，根据文档 ID 路由到目标主分片。
3. 主分片先执行写入。
4. 主分片再把变更同步到对应副本分片。
5. 当主分片和所需副本写入完成后，请求返回成功。

示意理解：

- 协调节点：负责接收请求和转发
- 主分片：负责处理真实写入
- 副本分片：负责复制数据

## 1.4 查询流程

一次搜索请求，大致分两阶段：

### Query Phase

- 协调节点把查询分发到相关分片
- 每个分片本地计算匹配结果和评分
- 每个分片先返回自己的 Top N

### Fetch Phase

- 协调节点汇总并排序各分片结果
- 再向命中的分片拉取最终文档内容
- 组装成响应返回给客户端

这也是为什么：

- 分片数过多会增加查询协调成本
- 深分页会显著拉高各分片计算开销

## 1.5 路由

默认情况下，OpenSearch 会根据文档 ID 把数据路由到某个主分片。

如果业务上需要让某类数据固定落在同一分片，可以指定 routing：

```json
PUT /orders/_doc/1001?routing=user_1
{
  "user_id": "user_1",
  "amount": 99
}
```

查询时也要带相同 routing，否则可能查不到：

```json
GET /orders/_doc/1001?routing=user_1
```

适用场景：

- 按租户路由
- 按用户路由
- 希望相关数据尽量落到同一分片

风险：

- 路由设计不均匀会造成热点分片

## 1.6 集群状态

`/_cluster/health` 常见状态：

- `green`：主分片和副本都正常
- `yellow`：主分片正常，但至少有副本未分配
- `red`：存在主分片不可用，部分数据不可读写

```bash
GET /_cluster/health
```

## 1.7 分片数不是越多越好

常见误区是“为了扩展性，先把分片开很大”。这通常会带来反效果：

- 小索引分片过多，会浪费内存和文件句柄
- 查询会扇出到更多分片，增加协调开销
- 运维复杂度变高

经验上：

- 小规模索引先保守设置分片数
- 预估数据规模、写入量、查询模式后再设计
- 比起盲目加分片，更重要的是按业务做好索引拆分策略
