# 一 OpenSearch 安全

OpenSearch 在生产环境中不能只关注查询和索引，还要控制“谁能访问、能访问什么、传输是否安全”。如果安全配置缺失，搜索集群很容易变成高风险入口。

## 1.1 安全的几个核心点

- 身份认证：你是谁。
- 权限控制：你能访问哪些索引、接口、字段。
- 传输加密：客户端到节点、节点到节点是否启用 TLS。
- 审计：谁在什么时间做了什么操作。

## 1.2 认证方式

常见认证方式包括：

- 基本认证：用户名 + 密码，最常见。
- 证书认证：基于客户端证书。
- 代理认证：由网关或反向代理先完成认证。
- 单点登录：对接企业身份系统。

最基础的访问示例：

```bash
curl -u admin:admin https://localhost:9200
```

生产环境里，不应长期保留默认账户、默认密码或弱口令。

## 1.3 权限控制

权限设计一般分三层：

- 集群级权限：例如查看集群健康、管理模板、创建快照。
- 索引级权限：例如读某个索引、写某个索引、删除某个索引。
- 文档级/字段级权限：限制用户只能看到部分文档或字段。

典型角色划分：

- 管理员：集群管理、模板、索引维护、快照恢复。
- 应用写入角色：只允许写指定索引。
- 应用查询角色：只允许读指定索引。
- 运维只读角色：只允许查看监控、健康状态和任务信息。

## 1.4 最小权限原则

不要让应用直接使用管理员账户。

更合理的做法：

- 写入服务只授予写入目标索引的权限
- 查询服务只授予读权限
- 运维脚本使用单独角色
- 高风险接口单独限制，例如删除索引、恢复快照、修改模板

## 1.5 TLS

安全传输至少要考虑两段链路：

- 客户端到 OpenSearch 节点
- OpenSearch 节点之间

如果未启用 TLS，风险包括：

- 用户名密码被窃取
- 查询请求和返回数据被中间人获取
- 节点间通信被伪造或篡改

因此生产环境建议：

- 外部访问统一走 HTTPS
- 节点间通信也启用 TLS
- 证书有明确签发和轮换策略

## 1.6 常见风险点

### 暴露公网

OpenSearch 不应直接暴露在公网。更合理的做法是：

- 放在内网
- 前面加 API 网关、堡垒机或反向代理
- 配合安全组、ACL、白名单

### 默认账户长期使用

初始化后应尽快：

- 修改默认密码
- 禁用不需要的默认账户
- 建立专用业务账户

### 应用和管理共用一套凭证

一旦应用泄漏凭证，管理能力也会一起泄漏。业务访问和管理访问应分离。

## 1.7 审计与可观测性

建议至少记录：

- 登录失败
- 权限拒绝
- 删除索引
- 修改模板
- 快照恢复
- 角色和用户变更

如果审计缺失，出了事故很难定位是谁触发了高风险操作。

## 1.8 实践建议

- OpenSearch 默认放内网，不直接暴露公网。
- 应用一律使用最小权限账户，不使用管理员账号。
- 认证、授权、TLS、审计应作为一套方案设计，而不是只配其中一个。
- 高风险操作要能追溯到具体人或具体服务。
