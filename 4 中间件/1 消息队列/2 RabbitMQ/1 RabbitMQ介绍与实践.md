# 1 RabbitMQ 介绍与实践

RabbitMQ 是实现 AMQP 的消息代理，核心对象包括生产者、交换机（Exchange）、队列（Queue）和消费者。生产者通常不直接把消息发到队列，而是把消息发布到交换机，由绑定规则路由到一个或多个队列。

## 1.1 交换机类型

| 类型 | 路由方式 | 常见场景 |
| :--- | :--- | :--- |
| direct | routing key 精确匹配 | 指定类型或任务路由 |
| topic | 使用通配符匹配 routing key | 多级事件主题 |
| fanout | 广播到所有绑定队列 | 多消费者订阅同一事件 |
| headers | 根据消息头匹配 | 特殊路由条件 |

队列通常由一个消费者组共享：同一队列中的消息会分发给其中一个消费者；需要每个服务都收到事件时，应为每个服务建立独立队列并绑定到交换机。

## 1.2 可靠投递

生产者确认（Publisher Confirm）用于确认 Broker 已接收消息；消费者手动 ack 用于确认业务处理完成。应根据业务决定 ack 时机：处理成功后再确认，失败时重试或进入死信队列。自动 ack 可能在业务处理前丢失消息。

持久化消息需要持久化交换机、队列和消息，并考虑磁盘、镜像/仲裁队列和恢复时间。持久化不等于业务一定不丢失，还要验证发布确认、消费确认、重试和备份策略。

## 1.3 重试、顺序与幂等

RabbitMQ 的重新投递可能导致重复消费。消费者应使用消息 ID、业务唯一键或状态机实现幂等。失败消息不要无限立即重回原队列，否则会造成热循环；可使用 TTL + 死信交换机实现延迟重试，并为最终失败消息提供人工查看和重放流程。

队列通常只保证队列内的相对顺序，多个消费者、重试和重新入队都会改变观察顺序。如果业务需要同一订单或账户有序处理，应按业务键分片，或在消费者侧检查版本号。

## 1.4 运维要点

监控队列深度、消费者数量、消费速率、消息年龄、未确认消息、发布确认失败、重试和死信数量。连接和通道应复用并设置上限；消费者应设置 prefetch，避免单个消费者一次占用过多未确认消息。
