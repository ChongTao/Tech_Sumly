# 1 Kafka介绍

Kafka 是一个分布式事件流平台，核心能力可以概括为三件事：

- 发布和订阅事件流
- 持久化存储事件流
- 对事件流进行实时处理或回放处理

它既可以被当作消息队列使用，也更适合作为事件驱动架构中的“事件总线”和“提交日志”。相比传统 MQ，Kafka 更强调高吞吐、可扩展、可回放，以及围绕 Topic/Partition 组织的顺序日志模型。

## 1.1 典型场景

- 业务解耦：下单、支付、发货、积分等系统通过事件解耦
- 异步削峰：把高峰请求先写入 Kafka，再由消费端按自身能力处理
- 日志与埋点采集：收集应用日志、行为埋点、监控指标
- 数据管道：将数据库变更、应用事件持续同步到搜索、数仓、湖仓
- 流式计算：对事件流做聚合、窗口计算、告警、规则判断

## 1.2 Kafka特性

Kafka 的特性可以从吞吐、扩展性、可靠性和消费模型几个角度理解。

- 高吞吐：顺序追加写、批量发送和批量拉取使 Kafka 很适合处理大规模消息流
- 可水平扩展：Topic 可以拆分为多个 Partition，Broker 和消费者都能横向扩容
- 高可用：Partition 支持多副本，Leader 故障后可以在同步副本中完成切换
- 持久化存储：消息会写入磁盘日志，不依赖消费者是否已经消费
- 可回放：消费者可以通过 Offset 自主控制读取位置，适合重试、补偿和历史重放
- 局部有序：单个 Partition 内的消息天然有序，适合按订单号、用户 ID 等维度保证顺序
- 解耦能力强：生产者与消费者通过 Topic 交互，不需要直接感知对方状态
- 同时支持队列和发布订阅语义：同一 Consumer Group 内分摊消费，不同 Group 间独立消费
- 投递语义丰富：可实现 at most once、at least once，以及基于幂等与事务的 exactly-once
- 生态完整：可与 Kafka Connect、Kafka Streams 等组件配合，构建完整的数据流平台

## 1.3 核心概念

### Topic

Topic 是 Kafka 中逻辑上的消息主题，生产者向 Topic 写入消息，消费者从 Topic 读取消息。

### Partition

Topic 会被拆成多个 Partition。每个 Partition 都是一条有序、只追加的日志。

- 顺序性只在单个 Partition 内保证
- 一个 Topic 的吞吐和消费并行度通常由 Partition 数决定
- 选择分区键时，应优先考虑业务局部有序性和热点均衡

### Broker

Broker 是 Kafka 集群中的服务节点，负责存储数据、处理生产与消费请求。

### Replica

每个 Partition 可以有多个副本：

- Leader：负责对外提供读写
- Follower：从 Leader 复制数据

副本机制用于提高可用性和容错能力。

### Producer

Producer 负责写入消息到 Kafka。写入时通常要决定：

- 发往哪个 Topic
- 如何选择 Partition
- 是否使用 Key 保证同 Key 数据落到同一 Partition
- 写入确认级别 `acks`

### Consumer

Consumer 负责从 Kafka 拉取消息。Kafka 使用拉模型而不是推模型，消费者主动 `poll` 数据。

### Consumer Group

多个 Consumer 可以组成一个 Consumer Group：

- 同一 Group 内，一个 Partition 同时只会分配给一个 Consumer
- 不同 Group 之间相互独立，都能消费同一份数据

这使 Kafka 同时具备“队列模型”和“发布订阅模型”的能力。

### Offset

Offset 是 Partition 内消息的位置编号。

- Consumer 的读取位置由 Offset 表示
- Offset 提交后，消费者重启时可以从已提交位置继续
- Offset 不是全局唯一，只在 Partition 内有意义

## 1.4 一条消息长什么样

Kafka 中的消息通常包含：

- Key：用于分区路由，也可用于按 Key 做日志压缩
- Value：业务负载
- Timestamp：消息时间戳
- Headers：扩展元数据
- Offset：写入后由 Partition 分配的位置

## 1.5 Kafka为什么高性能
### 1.5.1 顺序追加写

Kafka 的 Partition 本质上是一条只追加日志。消息写入时通常追加到文件末尾，而不是在磁盘中随机修改数据。

顺序写的好处：

- 磁盘寻道少，尤其对机械盘收益明显
- 写入模式稳定，容易被操作系统和文件系统优化
- 即使在 SSD 上，顺序写通常也比频繁随机写更高效

很多人误以为“落盘一定慢”。实际上，顺序写磁盘并不一定比随机写内存结构差很多，Kafka 正是利用了这一点。

### 1.5.2 利用操作系统页缓存

Kafka 大量依赖操作系统的 Page Cache，而不是自己重复实现一套复杂缓存。

好处：

- 生产者写入的数据会先进入页缓存，再由操作系统择机刷盘
- 热数据读取时，消费者常常直接命中页缓存，不一定每次都访问物理磁盘
- 减少了用户态和内核态之间重复拷贝与缓存管理的复杂度

这意味着 Kafka 的高性能不只是 Broker 自己快，而是充分借助了操作系统对文件 I/O 的优化能力。

### 1.5.3 批量发送与批量拉取

Kafka 不是一条消息一个请求地处理，而是大量使用批处理。

生产端：

- Producer 会把多条消息攒成一个 batch 再发给 Broker
- 减少网络往返次数
- 减少请求头、系统调用等固定开销

消费端：

- Consumer 每次 `poll` 也会批量拉取消息
- 提高网络利用率
- 降低频繁拉取带来的 CPU 开销

这类批处理对吞吐提升非常明显，尤其是在消息体较小时。

### 1.5.4 零拷贝减少数据复制

Kafka 在数据传输上会尽量减少用户态和内核态之间的不必要拷贝，典型做法是使用零拷贝机制。

它的价值在于：

- 减少 CPU 在数据复制上的消耗
- 减少上下文切换
- 提高网络发送效率

面试里可以简单概括为：Kafka 读取磁盘文件并通过网络发送给消费者时，会尽量避免“磁盘到内核、内核到用户态、再回内核、再发网卡”这种多次复制链路。

### 1.5.5 分区带来的并行能力

Kafka 的 Topic 可以拆分为多个 Partition，这直接带来并行处理能力。

- 生产端可以并行写多个 Partition
- Broker 集群可以把不同 Partition 分布到不同机器
- 消费端一个 Consumer Group 可以并行消费多个 Partition

所以 Kafka 的高性能不是单机硬扛，而是通过 Partition 机制把吞吐横向展开。

### 1.5.6 拉模型更适合高吞吐

Kafka 采用 Pull 模型，由消费者主动拉取数据，而不是 Broker 主动推送。

Pull 模型的优势：

- 消费者可以按自身处理能力控制拉取速率
- 可以自然做批量拉取
- 不容易因为消费者处理能力不一致导致 Broker 推送失控

这使 Kafka 在面对不同消费能力的下游系统时，更容易稳定地维持高吞吐。

### 1.5.7 数据结构简单

Kafka 的存储结构本质是日志追加加索引，不需要像传统消息系统那样频繁维护复杂的随机写元数据结构。

这种简单结构带来的好处：

- 写路径短
- 存储组织清晰
- 更适合顺序扫描和范围读取

### 1.5.8 生产者和消费者解耦

生产者只负责写入 Topic，消费者只负责按 Offset 读取，两者不直接耦合。

这带来的性能收益是：

- 生产速度不需要严格等待消费速度
- 消费端慢时，Broker 主要承担存储和分发，不需要实时推送协调
- 系统更容易做削峰填谷

### 1.5.9 压缩能力提高有效吞吐

Kafka 支持消息压缩，例如 `gzip`、`snappy`、`lz4`、`zstd`。

压缩的意义不只是省磁盘，还包括：

- 减少网络传输字节数
- 提高单位时间内可传输的消息量
- 在 CPU 够用时，往往可以显著提升整体吞吐

因此实际系统里说“Kafka 吞吐高”，有时是“物理吞吐高”，有时是“压缩后有效吞吐高”。

### 1.5.10 高性能不等于低延迟

这是面试里经常追问的一点。Kafka 追求的是高吞吐和可扩展，不一定是极致低延迟。

因为它会做：

- 批量聚合
- 页缓存写入
- 异步发送
- 副本复制

这些设计能提升吞吐，但某些情况下会增加单条消息延迟。所以 Kafka 更适合高吞吐事件流，而不是所有场景下都追求微秒级延迟。
