# 1 分布式锁

分布式锁用于让多个进程或节点在一段时间内互斥执行某项操作。它适合保护短临界区，不适合替代数据库约束、幂等设计或长时间持有的业务事务。

## 1.1 必要语义

- 互斥：同一资源通常只有一个持有者。
- 自动释放：持有者崩溃后锁最终能过期或被接管。
- 唯一持有者标识：释放时只能删除自己的锁。
- 续租或租约：任务超过 TTL 时要续期，并处理续租失败。
- fencing token：下游使用递增令牌拒绝旧持有者，防止网络分区后的陈旧客户端继续写入。

Redis `SET key value NX PX` 可实现基础租约锁，但释放必须校验 value；单机锁不能自动提供跨节点强一致。数据库唯一键、行锁、ZooKeeper/etcd 等方案应根据故障模型和性能需求选择。

加锁成功后不能假设业务一定能完成；业务操作必须可重试、幂等，并设置最大持有时间。锁超时后原持有者可能仍在执行，因此没有 fencing 的锁不能保护所有外部资源。

## 4 为什么需要分布式锁

在分布式系统中， **分布式式锁**是协调多个节点对共享资源进行互斥访问的核心机制，在分布式系统中，多个节点可能同时访问和修改共享资源，这可能导致数据不一致或者其它问题。为了避免这种情况，需要一种机制来确保任何时候只有一个节点能够访问和修改共享紫云，这就是分布式锁的作用。

### 4.1 解决分布式环境下资源竞争
在单机系统中，可以通过本地锁（如互斥锁）保证同一 进程内的线程安全。但在分布式系统中：

- **资源跨节点共享**：多个服务实例可能同时访问同一资源（如数据库、文件、缓存等）
- **竟态条件** ： 并发操作可能导致数据不一致。

### 4.2 保障操作的原子性与一致性
分布式锁确保同一时间只有一个节点能执行关键操作，从而：
- **避免重复处理**：防止任务被多个节点重复执行
- **保证事务隔离性**：在分布式事务中，确保中间状态不被其它操作干扰。
