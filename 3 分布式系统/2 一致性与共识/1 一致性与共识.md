# 1 一致性与共识

## 1.1 副本一致性

同步复制通常在多个副本确认后才返回，数据丢失风险低但延迟和可用性成本高；异步复制先向主副本确认，吞吐和延迟较好，但故障切换可能丢失最近写入。读副本延迟会导致读到旧值，应用要按场景选择强读、因果读或最终一致读。

## 1.2 共识问题

共识协议让多个节点在存在故障和网络延迟时，就某个值或日志顺序达成一致。它通常包含领导者选举、日志复制、提交和成员变更。Raft 以易理解为目标，常见实现包括选主、任期、日志匹配和多数派提交。

### Raft 脑裂：成因与处理
# Raft 脑裂：成因、危害、协议处理、工程增强
## 1. 定义
脑裂：集群发生网络分区，**多个节点同时认为自己是Leader**。
- ✅ 标准Raft：**同一任期term，最多只能选出1个合法Leader**；少数分区的旧Leader无法提交日志，不会造成两份已提交数据（安全）
- ⚠️ 表象：网络断连后，老Leader还活着、继续接收客户端请求，但写请求永远无法commit，不能返回成功给客户端。

## 2. 成因
1. **网络分区（根本原因）**
集群被切为两个隔离子网。例如5节点集群：{1,2,3}、{4,5}；原来Leader在{4,5}分区。
- {1,2,3}收不到老Leader心跳 → 超时发起选举，拿到3票（多数派），选出**新Leader，term+1**
- 老Leader（4,5侧）网络隔离，不知道已经产生更高term的新Leader，**依旧认为自己是Leader**
→ 出现两个节点自认为Leader（表象脑裂）

2. **极端工程场景（论文Raft不存在，生产实现会踩坑）**
- 节点长时间GC/OS暂停（STW），暂停时长超过选举超时；节点恢复后，不知道自己已经被剥夺Leader身份，继续对外提供服务（僵尸Leader/zombie leader）
- 不对称网络：A发消息能到B，但B回包丢包；心跳单向可达，造成误判
- 客户端直连老Leader，读到旧数据；或者写入请求被接受，但永远无法commit

> 集合论原理：两个多数派集合必然相交。同一个term，不可能同时选出两个Leader；只有不同term才会出现“两个自认为leader”。

## 3. Raft原生协议如何处理脑裂（核心机制）
1. **多数派选举（Quorum）**
Leader当选必须拿到 >n/2 的选票。网络分区后，最多只有一个分区能凑出多数派。另一分区（少数派）无法选出新Leader。

2. **日志提交必须多数派ACK**
老Leader虽然自认为Leader，但它所在分区是少数派，复制日志无法拿到多数节点ACK → **日志不能commit**，客户端写请求返回超时，不会返回成功。
> 关键点：未commit日志在分区恢复后会被新Leader日志覆盖，不会破坏已提交数据的一致性。

3. **任期（term）比较**
网络恢复后，老Leader收到新Leader的AppendEntries（心跳），发现对方term > 自己term，**自动step down降级为Follower**，停止作为Leader工作。

4. **选举随机超时**
降低同一分区内多个Follower同时发起选举的概率，减少无效选举震荡。

## 4. 原生Raft的短板（生产风险）
1. 老Leader仍会接收客户端读请求，返回过期数据（**读陈旧问题**）
2. 僵尸Leader：节点长时间阻塞恢复后，还对外提供服务，客户端写入被“假Leader”接收，但是无法提交，容易造成业务侧重试混乱
3. 读请求没有quorum校验时，脑裂期间读到脏数据

## 5. 工程上增强方案（etcd / TiKV / CockroachDB 使用）
| 方案 | 说明 |
|---|---|
| Leader Lease（租约） | Leader维持租约，租约到期自动下台；不依赖心跳，解决僵尸Leader。etcd实现。 |
| Fencing Token（隔离令牌） | 每次写携带递增的Leader令牌；存储层拒绝低令牌的旧Leader的写入，强制隔离旧主。 |
| Read Quorum（读多数派） | 读操作也要读取多数节点，避免从隔离的旧Leader读到过期数据。 |
| 集群节点奇数 | 集群节点总数用奇数（3/5/7），最大化容错能力；偶数节点没有提升容错，反而增加运维复杂度。 |

## 6. 故障恢复流程（网络分区愈合后）
1. 网络恢复，旧Leader收到更高term的AppendEntries RPC
2. 旧Leader发现对方任期更大 → step down，切换成Follower
3. Follower对比本地日志与新Leader日志，截断本地**未提交日志**，拉取新Leader日志补齐
4. 集群恢复单Leader正常工作；**已提交日志不会丢失，未提交日志丢弃**

## 7. 面试区分考点
- ❌ 错误：Raft网络分区会产生两个都能提交数据的Leader
- ✅ 正确：Raft不会出现双提交Leader；只会出现「少数分区旧Leader自认Leader，但无法提交写」的表象脑裂
- 对比：Redis脑裂是真脑裂，旧主还能成功写入并返回客户端成功，会丢数据；Raft不存在这个安全漏洞。



多数派不能解决所有问题：如果多数节点不可用，系统可能无法提交；脑裂时必须拒绝少数派写入；成员变更必须使用安全的联合配置或等价机制。客户端还要处理领导者变化、重试和重复提交。

## 1.3 CAP 与 PACELC

CAP 讨论网络分区发生时，在一致性和可用性之间的选择，不能被简单理解为“系统平时只能二选一”。PACELC 进一步指出，即使没有分区，也要在延迟和一致性之间权衡。选型时应以业务读写语义、故障目标和数据价值为准。

## 10 CAP理论及应用

# CAP理论及其应用
## 1. CAP 三个核心定义
CAP 定理：**分布式系统中，不能同时满足一致性(C)、可用性(A)、分区容错性(P)三者，最多同时满足两项。**

| 缩写 | 名称 | 含义 |
| ---- | ---- | ---- |
| C | Consistency 一致性 | 所有节点访问同一份最新的数据副本。任意时刻，任意节点读到的数据都是一样的。 |
| A | Availability 可用性 | 服务一直可用，每个客户端请求都能收到**非失败响应**（不一定是最新数据，但是能返回结果）。 |
| P | Partition Tolerance 分区容错性 | 网络发生分区（节点之间网络断开、丢包），系统仍然可以继续对外工作。 |

> ✅ 关键前提：**分布式系统P是必须的**。网络分区是客观必然会发生的故障，无法避免。
> 所以分布式系统实际只能二选一：**CP 或者 AP**，不存在CA。
> CA只存在于单机系统（没有网络，不存在分区，不需要考虑P）。

## 2. CP / AP 选型对比
| 类型 | 选择 | 特点 | 代价 | 典型系统 |
| ---- | ---- | ---- | ---- | ---- |
| CP | 一致性 + 分区容错，牺牲可用性 | 发生网络分区时，为保证数据一致，拒绝客户端请求，服务不可用 | 分区期间不可写/不可读 | ZooKeeper、etcd、Raft共识集群 |
| AP | 可用性 + 分区容错，牺牲一致性 | 网络分区时，每个分区独立对外提供服务，保证服务可用，但不同分区数据不一致 | 可能读到旧数据，分区恢复后需要数据合并、冲突解决 | Cassandra、DynamoDB、Eureka |

> ⚠️ 误区纠正
> 1. CAP不是三选一永久固定，**是网络分区发生那一刻才做取舍**。正常无分区状态下，系统可以同时保证C和A。
> 2. CAP中的一致性，是**强一致性**，不是最终一致性。最终一致性属于AP体系。
> 3. CAP不描述性能，和延迟、吞吐量无关。

## 3. 与Raft的关联
Raft 协议构建的集群（etcd）属于 **CP系统**：
网络分区出现时，只有拥有多数派的分区才能选出Leader，对外提供读写；少数分区节点拒绝写入，保证强一致，但少数分区侧客户端请求失败（牺牲A）。

## 4. 工程应用场景
### 场景1：元数据、配置中心、分布式锁 → CP（优先选强一致）
如etcd、zookeeper。
理由：元数据、锁信息一旦不一致会引发严重业务故障，宁可短暂不可用，也不能读到脏数据。

### 场景2：用户业务数据、高可用业务、注册中心 → AP（优先可用）
如Cassandra，Eureka。
理由：业务不允许服务完全不可用，可以接受短暂数据不一致，后台异步做数据修复。

## 5. 延伸：BASE理论（AP系统的落地理论）
BASE 是 CAP中AP方案的工程实现思想
- Basically Available：基本可用，故障时可以降级（限流、返回旧数据）
- Soft state：软状态，副本状态允许中间不一致，不需要时刻一致
- Eventually consistent：最终一致性，一段时间后所有副本数据会同步一致

## 6. 面试高频考点
1. 为什么不存在CA？
> 分布式环境网络分区P一定会发生；一旦分区出现，必须在C和A之间做取舍，无法同时保持C+A。CA仅单机。
2. CAP是静态永久选择吗？
> 不是。只有网络分区故障发生瞬间触发取舍，正常无故障时C和A可以同时具备。
3. CP是不是永远不可用？
> 不是。CP只是分区发生时，少数分区不可用；网络恢复后，集群自动恢复可用。
