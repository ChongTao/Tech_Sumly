# 1 微服务架构

微服务将系统拆为可独立开发、部署和扩展的服务，每个服务围绕业务能力拥有清晰边界。拆分本身不会自动提升性能，反而会引入网络、数据一致性、运维和测试复杂度。

## 1.1 服务边界

服务边界应依据业务能力、数据所有权、变更频率和团队责任划分。每个服务应拥有自己的数据写入口，跨服务访问通过 API 或事件完成，避免共享数据库表导致隐式耦合。

## 1.2 通信与数据

同步 RPC 适合需要立即结果的短操作；异步消息适合解耦、削峰和长流程。无论哪种方式都要定义超时、幂等、版本、错误和观测字段。

服务间最终一致性可通过 Outbox、事件驱动、Saga 和对账实现。不要把分布式事务、共享数据库或全局锁作为默认架构；先识别真正需要的业务不变量。

## 1.3 交付与运维

微服务需要统一的日志、指标、追踪、配置、身份、发布和回滚能力。服务健康检查应区分存活与就绪，发布要支持灰度和快速回滚。服务数量增长后，应警惕调用链过长、依赖环、版本矩阵和团队认知负担。
