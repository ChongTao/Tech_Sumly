# 分布式系统常见问题

## 什么是负载均衡？常见策略有哪些？

负载均衡把请求分配到多个健康实例，利用集群总容量并避免单个实例成为热点。服务发现提供可选实例，负载均衡策略结合实例健康状态和请求特征选择目标。负载均衡可以改善资源利用和故障隔离，但不能弥补集群总容量不足或共享依赖成为瓶颈。

| 策略 | 工作方式 | 适用情况与注意事项 |
| :--- | :--- | :--- |
| 轮询 | 按顺序把请求分给各实例 | 实例能力和请求开销接近时简单有效；不考虑实例当前负载。 |
| 加权轮询 | 按配置权重分配请求 | 适合实例规格不同的情况；静态权重无法及时反映运行时负载变化。 |
| 最少连接或最少活跃请求 | 选择当前连接数或处理中请求较少的实例 | 适合请求耗时差异较大的场景；连接数不一定能代表 CPU、队列或内存压力。 |
| 一致性哈希 | 根据用户、资源等键映射到实例 | 有利于缓存局部性或需要请求亲和性的场景；热点键会造成负载倾斜，扩缩容时通常配合虚拟节点减少映射变化。 |

负载均衡可部署在不同位置：DNS 通常按解析结果粗粒度分配，受客户端和递归 DNS 缓存影响；四层负载均衡按 TCP/UDP 连接分配，开销较低但不了解 HTTP 请求内容；七层代理可按路径、请求头或租户路由；客户端负载均衡则从服务发现结果中选择实例，减少代理跳数，但需要统一客户端行为和配置。

使用时要先过滤未就绪或不健康的实例，并观察每实例的请求量、延迟、错误率和队列。长连接、HTTP/2 或 gRPC 连接可能让连接级均衡看起来不均匀；会话粘滞能保持实例亲和性，但会影响故障转移和容量分配。相关内容：[服务发现与治理](<../6 服务发现与治理/1 服务发现与治理.md>)。

## 限流、降级、熔断分别是什么

在分布式系统或微服务架构中，**限流、降级、熔断**是保障系统高可用性和稳定性的核心策略。它们通过不同的机制应对高并发、故障和资源瓶颈问题，避免系统崩溃或服务雪崩。

| 能力 | 主要作用 | 常见做法 |
| :--- | :--- | :--- |
| 限流 | 把请求量或并发数控制在系统及依赖可承受的范围内，防止系统因突发流量过载。 | 按接口、租户或依赖设置配额；使用令牌桶、滑动窗口或并发数限制；超额请求可拒绝、排队或施加背压。 |
| 降级 | 负载过高或依赖不可用时，暂时减少非核心能力，尽量保留核心流程 | 关闭推荐等可选功能、返回有明确时效的缓存数据、改为异步处理；需要说明降级条件和返回结果的限制。 |
| 熔断 | 依赖持续超时或失败时，暂时停止向它发送请求，避免等待和失败继续占用资源 | 闭合状态正常调用；达到错误或慢调用阈值后进入打开状态并快速失败；经过冷却时间后用半开状态放少量探测请求，成功后恢复调用。 |

可以组合使用：入口限流控制总体负载；下游错误率或慢调用升高时熔断，保护调用方和依赖；非核心功能再通过降级提供缓存或简化结果。限流和熔断要按依赖、接口或租户设置边界，并结合超时、有限重试和隔离使用。对于支付、权限等关键流程，降级结果必须保持业务语义正确，不能用看似成功的默认值掩盖失败。

## 为什么需要分布式锁？

单机锁（例如进程内的互斥锁）只能协调同一进程中的线程。服务部署多个实例后，每个实例都有独立的锁；同一任务若同时到达不同实例，它们仍可能并发修改共享资源，造成重复执行、超额扣减或重复处理。

分布式锁通过共享的协调服务，为某个业务资源协调跨进程的临时所有权，常见场景包括：

- 多个服务实例中只允许一个实例执行某个定时任务。
- 同一订单、账户或库存项在短时间内需要串行处理。
- 避免多个实例同时执行同一项代价较高且不能并行的工作。

引入锁前先看能否用数据库唯一约束、条件更新、乐观锁或幂等处理直接保护业务不变量。这些机制通常更贴近数据本身，也减少额外的协调状态。分布式锁主要用于协调并发执行，不会自动提供跨服务事务或“业务只执行一次”的保证；租约过期时，旧持有者仍可能继续运行，下游写入需要结合 fencing token 或版本校验。

相关内容：[分布式锁](<../4 分布式锁/1 分布式锁.md>)。


##  分布式锁常见的实现方式有哪些？

常见方案依托数据库、Redis 或协调服务。实现方式会影响锁在故障切换、租约过期和网络分区时的行为，选型时应结合锁保护的资源和可接受的失败语义。

| 实现 | 常见机制 | 特点与注意事项 |
| :--- | :--- | :--- |
| 数据库 | 唯一键或条件更新、事务行锁、带过期时间的锁记录 | 可复用现有数据库，也便于把锁和业务更新放进同一个本地事务。高竞争会增加数据库负载；行锁适合短事务，不适合持锁执行长时间远程调用。租约记录还要处理过期和旧持有者继续执行的问题。 |
| Redis | `SET key token NX PX ttl`；通过 Lua 脚本校验 token 后释放或续租 | 延迟低、吞吐高，适合短租约互斥。创建、续租和释放要原子执行。主从异步复制的故障切换可能丢失锁状态；Redlock 依赖多个独立实例和多数派，仍需按时钟、网络和故障假设评估安全边界。 |
| ZooKeeper | 临时顺序节点；序号最小的客户端持锁，并监听前一个节点 | 会话失效后临时节点会被清理，顺序节点可让客户端有序竞争。需要多数节点可用，也要正确处理会话过期、中断和重新竞争。 |
| etcd 等协调服务 | 租约配合条件事务创建锁；可使用修订版本识别新旧持有者 | 基于共识的键值操作能提供明确的协调语义；失去多数节点时无法继续提交。若用修订版本作为 fencing token，下游存储也必须校验并拒绝较旧版本。 |

优先判断业务是否真的需要通用分布式锁。资源唯一性常可用数据库唯一约束或条件更新直接保证；必须跨进程互斥时，缩短临界区，并让下游通过 fencing token、版本检查或幂等机制拒绝过期操作。锁服务确认“获得锁”本身不能保证业务只执行一次。

相关内容：[分布式锁](<../4 分布式锁/1 分布式锁.md>)。

## CAP 理论是什么？在架构设计中如何应用？

CAP 描述分布式数据系统遇到网络分区时，一致性与可用性之间的约束。这里的一致性通常指线性一致性：操作看起来像按一个实时顺序原子执行，读操作能看到此前已完成的最新写入。

| 属性 | 含义 |
| :--- | :--- |
| 一致性（C） | 所有客户端观察到的操作结果符合单一、实时有序的历史；完成的写入不会被后续读操作当作不存在。 |
| 可用性（A） | 到达非故障节点的请求最终都得到响应；响应可以来自该节点当前的数据，因此不一定是最新值。 |
| 分区容错（P） | 节点间网络可能延迟、丢失消息或中断；系统需要定义网络分区期间如何继续运行。 |

网络分区发生时，系统不能同时保证所有请求都继续成功响应，并让所有读写都像访问同一份最新数据一样一致。分区容错不是可随意关闭的选项；设计需要明确分区时各类操作如何取舍：

| 分区期间的倾向 | 典型行为 | 代价 |
| :--- | :--- | :--- |
| 偏 CP | 需要多数副本或权威节点确认的操作，在无法确认时等待或拒绝，以保持一致的操作顺序。 | 少数派或无法联系权威节点的一侧可能暂时不能读写相关数据。 |
| 偏 AP | 分区两侧尽量基于本地数据继续响应，网络恢复后再传播和合并更新。 | 可能读到旧值或产生冲突，需要版本控制、冲突合并、补偿或对账。 |

CP 和 AP 是描述特定操作在故障条件下的行为倾向，并不代表一个产品的所有读写都只能归为同一类。实际设计可以按数据和操作设定不同语义。

应用 CAP 时，可以按以下步骤做决策：

- 先写清业务不变量和可接受的数据陈旧时间。例如账户余额、库存扣减和唯一性约束通常需要避免并发操作破坏约束；信息流和统计展示往往可以容忍短暂延迟，具体取决于业务要求。
- 对必须保持强一致的操作，指定权威写入方或多数派确认机制；无法确认时明确返回失败、处理中或稍后重试，避免给出虚假的成功结果。
- 对允许最终收敛的操作，定义事件 ID、幂等处理、版本比较、冲突合并和对账恢复规则。
- 明确分区恢复后的待处理写入、重复请求、冲突和用户可见状态，并通过故障演练验证这些行为。

CAP 主要讨论分区发生时的取舍；在没有分区时，系统仍可能在请求延迟和一致性之间权衡，PACELC 用于描述这一点。选型应依据业务读写语义、故障目标和数据价值，而不是只按 CP/AP 标签判断。
